# ИЗ НУЛЯ — правила разработки

Эти правила применяются ко всему проекту, включая вложенные папки.

## Контекст проекта

- Название: «ИЗ НУЛЯ».
- Жанр: браузерный 2D-симулятор жизни, карьеры и предпринимательства.
- Платформа: HTML5/JavaScript, ориентир на Яндекс Игры.
- Игрок начинает с минимальными ресурсами и постепенно развивает карьеру, навыки и собственные предприятия.
- Главный принцип: интересный игровой процесс, реалистичная и логически согласованная экономика, разнообразные интерактивные действия.
- В игре уже существуют экономические механики, профессии, бизнесы, товарный учёт, персонал, YouTube, музыка и другие системы. Развивай существующие системы с учётом их взаимосвязей.

## Обязательные правила

1. Перед изменениями изучай существующий код, зависимости, порядок инициализации модулей и связанные тесты. Проверяй текущее состояние Git и сохраняй изменения пользователя.
2. Не переписывай проект с нуля без прямого разрешения пользователя.
3. Не удаляй работающие механики ради упрощения реализации.
4. Избегай дублирования расчётов доходов, расходов, налогов и игровых ресурсов. Используй существующие функции расчёта и учёта; одна операция не должна учитываться несколько раз.
5. Сохраняй совместимость существующих игровых сохранений. При расширении формата обеспечивай корректное чтение старых данных и необходимые значения по умолчанию, без потери прогресса.
6. Не допускай появления денег, товаров или ресурсов без соответствующей игровой операции. Изменения баланса должны иметь понятный источник и согласованно отражаться в связанных системах учёта.
7. Проверяй загрузку игры и восстановление сохранений, включая сохранённую вкладку и прогресс после перезагрузки. Первый экран должен отображаться после регистрации всех необходимых модулей.
8. После изменений запускай существующие Node.js-тесты и Playwright-тесты. Не считай один набор заменой другого.
9. Если тесты не прошли, сообщай об этом явно. Не скрывай ошибки. Указывай неуспешные проверки, причины и доступные диагностические материалы. Если запуск невозможен, явно сообщай, что не проверено и почему.
10. Не изменяй тесты только для того, чтобы скрыть реальные дефекты. Не ослабляй проверки и не отключай падающие тесты ради успешного отчёта. Изменение ожидаемого поведения теста должно быть обосновано требованиями задачи.
11. Все новые игровые механики должны иметь понятный интерфейс и тесты. Проверяй реальные действия игрока и их результат; не подменяй прохождение прямым изменением состояния игры в браузерных сценариях.
12. Учитывай мобильные устройства и управление касаниями: доступность элементов, читаемость, размеры интерактивных областей и отсутствие обязательной зависимости от наведения мышью.
13. Не выдавай условные экономические коэффициенты за проверенную статистику России. Отделяй игровые допущения от подтверждённых данных; для подтверждённых данных указывай источник, дату и область применимости.
14. Делай изменения небольшими, понятными и пригодными для проверки через Git. Ограничивай изменения задачей и избегай несвязанного рефакторинга.
15. Не выполняй Commit, Push, удаление больших частей проекта или установку новых тяжёлых зависимостей без согласия пользователя. Подготовь понятное описание предполагаемого действия и получи согласие до его выполнения.
16. Всегда отвечай пользователю и составляй отчёты на русском языке.

## Порядок работы

1. **Анализ задачи.** Изучи требования, существующую реализацию, зависимости, сохранения и возможное влияние на другие системы.
2. **Краткий план реализации.** Обозначь предполагаемые изменения и способ их проверки. Для действий из правила 15 получи согласие пользователя.
3. **Изменение файлов.** Внеси минимальные необходимые изменения, сохраняя работающие механики и совместимость данных.
4. **Проверка работоспособности.** Проверь реальный пользовательский сценарий, загрузку игры, восстановление сохранений и затронутые интерфейсы.
5. **Автоматические тесты.** Запусти все существующие Node.js-тесты и Playwright-тесты. Для нового поведения и исправленных ошибок добавь необходимые проверки.
6. **Отчёт об изменениях и оставшихся ограничениях.** Перечисли изменённые файлы, результат работы, выполненные проверки, количество прошедших и не прошедших тестов, известные проблемы и непроверенные области.

## Запуск существующих тестов

Node.js-тесты находятся в корне проекта в файлах `tests*.js` и запускаются отдельно от браузерных. В PowerShell выполни:

```powershell
$failedTests = @()
$testFiles = @(Get-ChildItem -File -Filter 'tests*.js' | Sort-Object Name)
foreach ($testFile in $testFiles) {
    Write-Output ('RUN ' + $testFile.Name)
    node $testFile.FullName
    if ($LASTEXITCODE -ne 0) { $failedTests += $testFile.Name }
}
Write-Output ('Всего: ' + $testFiles.Count + '; прошло: ' + ($testFiles.Count - $failedTests.Count) + '; не прошло: ' + $failedTests.Count)
if ($failedTests.Count -gt 0) { throw ('Не прошли: ' + ($failedTests -join ', ')) }
```

Браузерные тесты находятся в `e2e/`. Запуск: `npm run test:e2e`. Playwright автоматически запускает локальный HTTP-сервер. Отчёт сохраняется в `playwright-report/`, диагностические материалы при падениях — в `test-results/`.

## Критерии готовности задачи

- Запрошенный функционал работоспособен и проверен через реальные действия игрока.
- Нет известных критических регрессий, вызванных изменениями; работающие механики и совместимость сохранений сохранены.
- Добавлены необходимые тесты для нового поведения и исправленных дефектов; существующие Node.js- и Playwright-тесты проходят.
- Предоставлен понятный отчёт на русском языке с изменёнными файлами, результатами проверок и оставшимися ограничениями.
- При неустранённых критических ошибках или невыполненных обязательных проверках не объявляй задачу полностью готовой; явно зафиксируй её фактическое состояние.
