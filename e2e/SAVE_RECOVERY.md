# Аудит и стабилизация сохранений «ИЗ НУЛЯ»

Дата: 15.10.2026. Игровой баланс и механики сохранены. Commit и Push не выполнялись.

## Обнаруженные и воспроизведённые ошибки

Первый набор новых Node.js-регрессий содержал 18 сценариев: **3 прошли, 15 не прошли** на исходной реализации. Исправления вносились после воспроизведения. Дополнительные проверки отдельно подтвердили возможность загрузить повреждённый ролик с будущими `NaN`, обнулить отсутствующий складской остаток и потерять отсутствующие отметки уплаченного налога.

| Проблема | Причина в исходниках | Решение |
| --- | --- | --- |
| Повреждённый JSON молча превращался в новую игру | Начальная загрузка `game.js` использовала `initial()` при любой ошибке; следующая навигация могла перезаписать исходник | Экран восстановления, сохранение основного ключа, блокировка автосохранения и игровых действий |
| Неизвестная версия также сбрасывала прогресс | Проверка только `version !== 3` с заменой состояния | Явная ошибка версии без автоматического преобразования в новую игру |
| Правильный JSON с неверными вложенными типами ломал модули | Проверялись лишь отдельные корневые поля; `if(!block)` не чинит частично заполненный блок | Проверка структуры до выполнения модулей, нормализация совместимых отсутствующих полей на копии |
| Ошибка импорта могла испортить текущий прогресс и хранилище | `S=obj; save(); render()` выполнялось до успешного отображения | Единая загрузка: проверка копии, миграция, резервирование, пробный рендер без промежуточных записей, итоговая запись; возврат прежнего состояния при ошибке |
| Кнопка сообщала об успехе при переполнении/запрете localStorage | Обработчик безусловно показывал «Сохранено» после `save`, который не возвращал результат | Булев результат `save`, предупреждение и постоянная отметка «Не сохранено» на кнопке |
| Договор оставался активным после reload без мини-игры | Сохранялся `contracts11.active`, но не `modal` и сессия задания | Активное незавершённое действие освобождается с предупреждением, без начислений; договор можно начать заново |
| Старая премия срочного заказа могла попасть в обычную смену | Сохранялся `world.activeOffer`, а после загрузки или закрытия мини-игры он не очищался | Принятое предложение возвращается в доступные, активная связь снимается при загрузке/закрытии |
| Промежуточное сохранение могло содержать временную зарплату договора без отмены | Несколько обёрток `workResult` сохраняли разные стадии одной операции | Накопление запросов сохранения до завершения всей цепочки; запись только итогового снимка |
| Отсутствующие/устаревшие счётчики могли повторно использовать ID | Ленивые значения по умолчанию не резервировали ID существующих счетов и записей | Счётчики восстанавливаются с учётом имеющихся записей и завершённых счетов; небезопасные значения отклоняются |
| Потеря `claimed` могла повторно открыть уже выданную награду | Список достижений не проверялся и не связывался с конкретной проводкой | Новые награды содержат `missionId`; известные связи восстанавливаются, неоднозначные старые данные отклоняются |
| Повреждённые опубликованные видео могли портить дальнейшее состояние | Не проверялись параметры, используемые суточной симуляцией | Обязательные параметры ролика проверяются до загрузки, безопасные счётчики дополняются |
| Отсутствующий товар/налоговая история могли выглядеть как пустые | Часть структур создавалась с нулевыми значениями | Потерянные складские количества, известные товарные операции без склада и платежи НПД без таблицы отметок требуют восстановления исходника |

## Единый путь восстановления

Используется существующий формат **`version: 3`**, без второго игрового формата. Новое поле `pendingAction` необязательно для старых сохранений. Неизвестные дополнительные безопасные поля JSON сохраняются, а не выкидываются при нормализации.

`game.js/prepareSaveState` проверяет копию: корень, обязательные ресурсы, типы коллекций, проекты, основные экономические блоки, записи журнала, налоги, сотрудников, склад, поставки, договоры, видео и счётчики. Запрещаются нечисловые/бесконечные числовые значения, небезопасные ключи прототипа, недопустимая вложенность и неподдерживаемые версии. Существующие миграции ID проводок и склада переиспользованы.

`loadLocalState` применяет проверку до регистрации зависимых модулей. `restoreSaveState` применяется при JSON-импорте и облачной загрузке. Рендер кандидата не может записать его промежуточное состояние; при ошибке исходные `S`, вкладка и основной ключ сохраняются. Чтение файла обрабатывает также отмену выбора и ошибку FileReader.

При повреждённом локальном сохранении `initial()` используется только как внутренняя заглушка для регистрации модулей. Пользователь видит экран ошибки с причиной и путями проблемных полей, а не новую игру. Кнопки позволяют скачать исходник/резервную копию, повторить чтение, импортировать исправленный файл или явно начать новую игру с подтверждением. При доступном настоящем `yandexPlayer` можно восстановиться из облака. Автосохранение повреждённый исходник не заменяет.

## Что восстанавливается

- Обычные сохранения v3 с деньгами, долгом, имуществом, навыками, бизнесами, персоналом, журналом и игровыми отметками.
- Более ранние сохранения того же формата v3 без новых служебных счётчиков и целых ещё не существовавших подсистем.
- Частично заполненные совместимые блоки: отсутствующие служебные настройки, события, метрики, пустые новые коллекции, счётчики. Изменения отмечаются предупреждениями.
- ID финансовых проводок и старые налоговые ссылки — существующей миграцией без проводок и нового начисления.
- Старые складские данные — существующей миграцией с сохранением оплаченного товара, очереди и старых прав возврата, если исходные количества/цены известны.
- Счётчики счетов, договоров, предложений, поставок, персонала и видео — выше уже занятых ID.
- Отметки выданных наград, если в проводках есть однозначный `missionId`.
- Уже завершённые договоры, дебиторка и уплаченные налоги не исполняются заново при загрузке.

Отсутствующие деньги, долг, имущество, проекты или журнал не заменяются догадками. Отсутствующие энергия, часы, стресс или навыки у уже начатой игры также требуют исправления исходника. Начальные значения допустимы только там, где нет признаков начатого прохождения; это не выдача новых ресурсов посреди игры.

## Незавершённые действия и границы записи

Точное продолжение с сохранённого этапа не добавлено. Рабочая мини-игра, глубокое задание, бизнес-практикум и черновик редактора не списывают стоимость выполнения до завершения; новый маркер `pendingAction` позволяет явно сообщить об их прерывании. При reload они отменяются без дохода, расхода или бесплатного продвижения. Договор/срочное предложение освобождается; пользователь начинает выполнение заново. Сроки предложений сохраняются.

Завершённые действия сохраняются как раньше: проведённые деньги, товары, видео, начисленные счета и награды не отменяются. Прерывание игрового действия не является откатом уже оплаченной поставки или опубликованного ролика.

`installSaveBoundaries`, устанавливаемый после всех модулей, объединяет внутренние сохранения `workResult` и `advanceDay`. При успешном завершении пишется итоговое состояние; исключение откатывает изменения `S` и не сохраняет частичный результат. Ошибка localStorage оставляет последний сохранённый снимок, а текущая работа остаётся в памяти с предупреждением экспортировать JSON до закрытия страницы. Это не универсальная транзакционная система для всех игровых команд.

Рекламный callback привязан к состоянию и дню, для которых был начат запрос. После замены игры запоздалый callback не выдаёт награду новому прохождению. Существующая проверка `lastAdDay` сохраняется.

## Резервные копии

Используются сырые JSON-строки того же состояния, без альтернативной схемы:

| Ключ localStorage | Содержание |
| --- | --- |
| `iz_nulya_v3_state` | Основное состояние |
| `iz_nulya_v3_state_backup` | Предыдущая запись перед очередным изменением основного снимка |
| `iz_nulya_v3_state_recovery` | Защищённый исходник до нормализации либо предыдущее основное состояние перед последним явным импортом/облачной загрузкой/новой игрой |

Обе копии скачиваются через справочник. Повреждённый текущий исходник скачивается с экрана восстановления как есть. `_backup` обновляется при последующих сохранениях; `_recovery` не обновляется обычной навигацией, но заменяется следующим явным восстановлением/заменой игры. Это ограниченные резервные копии, не бессрочный архив всех версий.

Если создать необходимую копию или записать основной снимок нельзя, замена не выполняется. Нельзя обещать сохранение новой работы после запрета доступа/исчерпания квоты; пользователь получает предупреждение и возможность экспортировать состояние в JSON.

## Облако

`simulation_v8.js/cloudSaveV8` и `cloudLoadV8` используют реальный интерфейс Яндекс Игр только при наличии игрока. Сохранение остаётся ручным, внутренний порог размера — прежние 190000 байт. Загрузка запрашивает подтверждение и использует общую проверку/восстановление с локальным резервированием. Повреждённые облачные данные не заменяют локальный прогресс. Перечитывание одной облачной версии не начисляет операции.

В Node.js проверены адаптер и round trip с моками `getData/setData`. Реальная авторизация, платформа, сетевые конфликты и её квоты в этой локальной среде не проверялись.

## Неподдерживаемые случаи и риски

1. Форматы с `version`, отличным от 3, не мигрируются: подтверждённых схем других корневых форматов в исходниках нет. Это отличается от старых версий самой игры, которые сохраняли тот же v3.
2. Точный этап мини-игры, музыкальный паттерн и содержимое неопубликованного видеочерновика не возобновляются. Новые прерывания явно предупреждаются; для старых обычных сессий без маркера факт прерывания не всегда можно определить.
3. Нельзя достоверно восстановить утраченные обязательные ресурсы, индивидуальную историю продаж/оплат или старый неоднозначный список наград. Исходник сохраняется, причина отказа показывается.
4. Проверка структуры не доказывает истинность вручную изменённых, но внутренне правдоподобных значений. Серверной верификации/античит-модели нет.
5. Одновременная игра в нескольких вкладках не имеет разрешения конфликтов: остаётся риск конкурирующих записей. Также не добавлялись межустройственные слияния облачного прогресса.
6. Хранилище и резервные копии имеют ограниченный объём. Работа после отказа записи остаётся только в памяти до экспорта/успешного сохранения. Копии внутри localStorage не защищают от полной очистки данных браузера.
7. Вспомогательная `iznulya_deep_v13_history` записывается отдельной веткой `deep_v13.js`, но не восстанавливается в основной `S`; это не источник денежных операций. Полное сохранение UI/вспомогательных историй и архивирование длинного финансового журнала остаются отдельными задачами.
