# Стабилизация идентификаторов финансового журнала — 15.10.2026

Исправлена генерация ID проводок и их восстановление из старых сохранений.

## Первопричина и воспроизведение

`game.js/book` назначал `id = S.ledger.length + 1`. Когда длина превышала 12000,
журнал сокращался до последних 10000 строк, а ID следующих операций возвращался
к 10001, хотя запись с таким ID могла ещё находиться в журнале.

До исправления 12002 вызова настоящего `book` дали:

```text
Записей: 10001
Уникальных ID: 10000
Последние ID: 12000, 12001, 10001
```

Поиск по подключённым игровым скриптам подтвердил: записи в `S.ledger` создаются
только в `book`. `econPost` и обёртка региональной оплаты вызывают его.

Связанные сущности имеют самостоятельные пространства идентификаторов:

| Источник | Что идентифицирует | Генератор |
| --- | --- | --- |
| `game.js/book` | Проводку финансового журнала | Теперь `allocateLedgerId()` |
| `economy.js/econInvoice` | Счёт в общей дебиторской задолженности | `economy.seq++` |
| `contracts_v11.js/newOffers11` | Предложение и связанный профессиональный договор | `++contracts11.seq` |
| `suppliers_v26.js/order` | Поставку | `nextShipmentId` |
| `youtube_business_v17.js/accept`, `plan` | Рекламный договор или календарную запись | `state().seq++` |
| `world.js/newOffer`, `simulation_v8.js/refreshLabour` | Предложение работы | `nextOffer++`, `++labour8.seq` |
| `youtube_v15.js/create`, `strategy_v10.js/createStrategicRelease` | Ролик или выпуск | Собственные счётчики последовательностей |

Эти ID сущностей не являются ID проводок; их счётчики и связи не изменялись.

## Реализация

- В `S` добавлено сохраняемое поле `nextLedgerId`; новая игра начинает с 1.
- `allocateLedgerId` выдаёт следующий безопасный целый ID, независимо от длины
  журнала. Обрезка журнала не меняет счётчик. При исчерпании диапазона safe integer
  операция отклоняется до изменения денег, вместо выдачи повторного ID.
- `initializeLedgerIds(state)` применяется при обычном чтении localStorage,
  JSON-импорте и облачной загрузке, до использования восстановленного журнала.
- Счётчик старого сохранения определяется по максимальному ID сохранённых строк,
  сохранённому значению счётчика и ключам налоговых отметок. Уже существующий
  больший счётчик сохраняется, даже если соответствующие строки удалены.
- Первый корректный экземпляр ID остаётся прежним; повторные и некорректные ID
  получают новые значения выше предварительно найденного максимума. Нормализация
  повторной загрузки не меняет уже исправленные ID.
- Ссылки налогового кабинета `tax.records` переносятся на перенумерованные строки
  с сохранением `kind` и `paid`. Оставшиеся ссылки на удалённые строки резервируют
  свои номера, чтобы новый доход не унаследовал старую отметку уплаты.
- Миграция не вызывает `book`, оплату налогов или погашение счетов. Не изменяются
  суммы, количество и порядок старых проводок, деньги, долг и статусы договоров.
  Версия сохранения остаётся 3; поле счётчика добавлено совместимым расширением.

Связанное исправление: `contracts_v11/workResult` и `labour_v19/workResult`
искали новые проводки через `slice(предыдущая длина)`. Если обычная оплата внутри
этого вызова сокращала журнал, поиск возвращал пустой результат: договор мог
не сторнировать немедленную оплату, а аналитика теряла смену. Теперь обе функции
запоминают следующий ID и отбирают проводки начиная с него. Это изменение связано
только с корректной обработкой обрезки журнала.

## Совместимость и границы восстановления

Если старый ID уже относился к нескольким строкам, прежняя налоговая модель
использовала одну общую отметку для всех этих строк. Из старого JSON невозможно
достоверно восстановить, какой именно строке игрок первоначально назначил отметку.
Миграция сохраняет прежнюю интерпретацию для каждой строки, включая `paid: true`;
она не пытается пересчитать и повторно взыскать прошлые налоги, автоматически
вернуть деньги или исправить исторические экономические последствия коллизии.

Если старый журнал и ссылки полностью удалены, а счётчика в таком старом сохранении
никогда не было, максимум утраченных ID восстановить невозможно. Номера остаются
уникальными относительно доступной истории и ссылок. После появления `nextLedgerId`
дальнейшая обрезка или очистка журнала не сбрасывает последовательность.

Надёжность настоящего SDK облачного хранения здесь не подтверждается: облачный
путь проверен в Node.js с тестовым адаптером. Существующие ограничения годового
налогового расчёта по обрезаемой истории, склады, прогнозы и другие выявленные
архитектурным анализом проблемы в этой задаче не менялись.
